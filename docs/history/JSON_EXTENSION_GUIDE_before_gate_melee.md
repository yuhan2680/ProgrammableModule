# JSON 扩展指南：胜利条件、模块与地块

适用工程：可编程模块（ProgrammableModule）。核对日期：2026-09-11。

本文以现有代码为依据，说明内容作者如何写 JSON，以及程序员如何让新的配置真正生效。文末提供可单独保存为文件的存活时间关卡、攻击模块、障碍物地块示例。**本文没有实现存活时间或攻击系统，也没有把示例安装进游戏。**

## 1. 先区分“增加内容”与“增加能力”

JSON 保存参数和引用；GDScript 决定这些参数如何参与游戏。往 `properties` 中添加字段，不会自动产生相应玩法。

| 要做的内容 | 当前只写 JSON 是否足够 | 原因 |
| --- | --- | --- |
| 改变终点坐标、判定半径 | 是 | 已有到达终点的判定代码 |
| 存活指定秒数后获胜 | 否 | 当前没有计时胜利条件，也没有死亡系统 |
| 修改移动模块的速度、尺寸、名称和图片 | 是 | 可以复用已注册的 `MovementModule` |
| 新增攻击模块 | 否 | 还没有攻击行为、伤害结算或攻击语言指令 |
| 新增不可通行的障碍物地块 | 是 | 已有 `collision: true` 的地形阻挡逻辑 |
| 地块减速、持续伤害或可破坏 | 否 | 需要代码读取对应属性并执行效果 |

这里的“是”还要求图片存在、内容 ID 有效，并且关卡正确引用了该内容。通过 JSON 语法检查、通过内容加载、通过关卡校验、通过装配确认、玩法实际运行，是不同的检查阶段。

## 2. 文件放在哪里，如何被游戏读取

### 2.1 目录

| 内容 | 工程内置目录 | 玩家外部目录 | 说明 |
| --- | --- | --- | --- |
| 模块定义 | `res://data/modules/` | `user://data/modules/` | 每个 JSON 根对象描述一种模块 |
| 地块定义 | `res://data/tiles/` | `user://data/tiles/` | 每个 JSON 根对象描述一种地块 |
| 完整关卡地图 | `res://data/levels/` | `user://levels/` | 地图中包含地块、出生点及关卡规则 |
| 图片 | 例如 `res://assets/` | 例如 `user://assets/` | 由定义里的 `texture` 明确引用 |

`res://` 是工程资源目录；开发时 `res://data/modules/a.json` 对应工程下的 `data/modules/a.json`。`user://` 是 Godot 的用户数据目录，Windows 默认通常位于 `%APPDATA%/Godot/app_userdata/ProgrammableModule/`，以游戏实际使用的路径为准。

目录只扫描直接位于该目录中的 `.json` 文件，不递归扫描子文件夹。模块与地块分别检查重复 ID；同类重复 ID 会导致本次内容加载失败，并保留上一次完整注册表，不能靠文件名或载入顺序覆盖已有定义。建议使用 `example.attack` 一类带前缀的 ID。

完整关卡没有独立于地图的第二份配置文件。**胜利条件位于地图的 `properties.level.goal`，当前没有扫描 `goals/` 或 `conditions/` 的机制。**只把一个 `goal` 对象保存成文件放入 `levels/`，不能作为关卡导入。

`data/maps/movement_lab.json` 目前是编辑器样例，不进入正式选关列表；它与关卡采用同一地图格式。

### 2.2 安装与重载顺序

1. 先准备图片，再放入模块或地块定义。
2. 在地图编辑器点击“重载内容”。正常游戏入口在从主菜单点击“开始游戏”时也会重载内容。
3. 编辑地图，引用已经加载的模块 ID 和地块 ID。
4. 编辑器的“开始测试”直接使用当前未保存地图与当前内容注册表，先组装再编程。
5. 要放入正常选关页面，再把完整地图保存或复制到关卡目录；点击“＋”可打开用户关卡文件夹，返回游戏后刷新。

仅刷新关卡列表不等于重新扫描模块目录。模块、地块文件中不能混放完整关卡；关卡目录也不能放单独的模块定义。

### 2.3 JSON 通用要求

- 使用标准 JSON：双引号、没有注释、没有尾随逗号，根节点为对象。建议保存为 UTF-8。
- 当前模块、地块、地图的 `format_version` 都只能是 `1`。
- 内容 ID 使用 `A–Z`、`a–z`、`0–9`、`_`、`-`、`.`，长度为 `1..128`；保留名称 `void` 不可使用。文件名用于组织文件，真正引用以 `id` 为准。
- 数值必须有限；数字字符串、布尔值不能代替数字。不要写 `NaN`、`Infinity`。
- 单个 JSON 文件上限为 `8 MiB`，嵌套深度不超过 `32`；名称等文本字段有长度限制，通常最多 `65536` 字符。
- `texture` 必须使用 `res://` 或 `user://`，路径分隔符为 `/`，不能包含 `..`、`.` 路径段或反斜杠。
- 图片支持 PNG、JPG/JPEG、WebP、SVG；路径合法还不够，文件必须存在并能够解码。JSON 中写一个尚不存在的图片名会阻止该定义加载。
- 对应 Schema 在 `schemas/module.schema.json`、`tile.schema.json`、`map.schema.json`、`level.schema.json`。Schema 帮助编辑和检查结构，运行时仍会校验引用、图片、坐标及实际占地。

## 3. 胜利条件怎么扩展

### 3.1 当前已支持的格式

胜利参数放在完整地图的 `properties.level.goal` 中：

| 字段 | 当前含义 | 当前约束 |
| --- | --- | --- |
| `goal.position.x` / `y` | 终点的地图坐标 | 有限数值，位于地图内 |
| `goal.radius` | 终点判定半径，以格为单位 | 默认 `0.25`，必须 `0 < radius <= 0.25` |
| `goal` 省略或为 `null` | 自由测试，无胜利目标 | 程序完成不触发通关 |

当前判定的是**机器中心**是否进入或经过圆形终点区域。每个逻辑 tick 检查本次移动线段，避免高速越过终点时漏判。终点的包围矩形必须完全位于可通行地形上；它是关卡标记，不是地块定义。

目前 `LevelDefinition._read_goal()` 不读取 `type` 字段。因此：

- 只写 `type: survive_time` 和时间，没有 `position`，现有游戏会拒绝该关卡。
- 如果又补上合法的 `position`，现有游戏会忽略 `type` 和时间，仍按到达终点判胜。这不是兼容实现。
- 改成 `win_condition`、`victory_conditions` 等新字段，当前代码也不会自动读取它们。

### 3.2 建议的新格式：用类型区分参数

以下是**后续实现建议，尚未支持**。继续使用 `properties.level.goal`，在目标对象中加入 `type`，让不同条件使用各自的参数：

| 建议类型 | 专用参数 | 建议含义 |
| --- | --- | --- |
| `reach_position` | `position`、`radius` | 保留现有到达终点行为 |
| `survive_time` | `duration_seconds` | 玩家存活达到指定模拟时间 |

`type` 是解析器识别的配置标签，不是文件路径，也不会自动实例化同名类。存活目标不需要 `position` 或 `radius`。

本指南的方案每关仍只有一个目标。不使用数组隐含“全部满足”或“任意满足”；以后需要组合条件时，再明确增加组合类型、子条件结构和 AND/OR 语义。

### 3.3 向后兼容和校验

建议按以下顺序修改读取规则：

1. `goal` 省略或为 `null` 时，继续按自由测试处理。
2. 对象没有 `type` 时，按照旧版 `position` / `radius` 读取，保证第一关和旧地图仍能使用。
3. 对象有 `type` 时，严格选择对应类型的校验器；未知类型直接返回明确错误。
4. `reach_position` 检查现有坐标、半径与地形要求；`survive_time` 只检查自己的参数。`duration_seconds` 必须为有限正数，不接受字符串、布尔值或非正数。
5. 更新 `level.schema.json` 的 `goal` 定义，使用互不重叠的分支区分旧格式、位置目标和存活目标。旧格式分支应限制为“没有 `type`”，避免带新类型的对象误落入旧分支。
6. 保存时保留其他关卡属性和未知扩展数据，不因修改目标而覆盖模块上限、可用模块列表或作者内容。

添加新字段不等于完成版本兼容。文末提案暂沿用地图容器的 `format_version: 1`，但仍要求升级后的目标解析器；**它不代表当前版本支持这些目标。**将来若改变整个地图格式版本，需要同时实现旧版本读取或迁移，不能只把 JSON 数字改为 `2`。

### 3.4 存活时间需要先规定什么

为了让文末示例有明确含义，建议实现时采用以下约定；这些不是当前游戏已经具备的行为：

| 情况 | 建议规则 |
| --- | --- |
| 计时起点 | 成功点击“运行程序”并创建世界后，从零开始；组装和编程耗时不计入 |
| 时间来源 | 使用模拟 tick，当前每秒 `10` tick；`60` 秒对应 `600` tick |
| 非整 tick 时长 | 按 `ceil(duration_seconds × TICKS_PER_SECOND)` 换成所需 tick 数，不能提前获胜 |
| 暂停 | 不推进世界，也不增加存活时间 |
| 停止、重开或重新运行 | 结束本次计时；新运行从零开始 |
| `main()` 正常执行完 | 玩家仍活着时，继续推进世界与存活目标，不立即失败或停止计时 |
| 程序语法或执行错误 | 仍报告本次运行失败；不要把错误当成“继续存活” |
| 玩家死亡 | 立即失败；死亡和达标发生在同一 tick 时，建议死亡优先 |
| 达到时间要求 | 发出一次完成通知，结束本次运行 |

**当前没有血量、死亡、敌人 AI 或伤害系统。**只加一个计时器，最多能实现“等待指定模拟时间”，还不能代表有死亡风险的存活玩法。真正实现存活条件时，需要先提供统一的玩家存活状态或死亡事件；不能把机器暂时没有移动能力直接等同于死亡，也不应为了判断死亡而引入额外 Core 模块。

当前调度还需要配套调整：`ProgramRunner` 在执行移动时推进世界，程序完成后不再推进；`GameSession` 对有终点的关卡会在程序结束但未到达目标时失败。存活条件不能沿用这两个分支不变。需要让程序完成后的存活会话继续驱动世界，同时避免解释器和会话在同一轮各推进一次 tick。空的 `main()` 也应按上表处理。

### 3.5 胜利条件的代码接入位置

| 文件或层 | 要修改的职责 |
| --- | --- |
| `scripts/gameplay/level_definition.gd` | 解析目标类型、验证参数；不能继续只用 `has_goal` 推断一定存在终点坐标 |
| `scripts/game/game_session.gd` | 启动和重置目标状态、每 tick 判定、失败优先级、一次性完成通知 |
| `scripts/language/program_runner.gd` 与会话调度 | 协调程序完成后继续模拟，保证世界每次只推进一次 |
| 新的目标判定类（建议） | 将目标定义与每次运行的计时等状态分离，避免所有目标堆进 `_check_outcome()` |
| `scripts/ui/playfield_canvas.gd`、`game_workbench.gd` | 只对位置目标绘制终点；时间目标显示剩余时间或进度 |
| `scripts/editor/map_editor.gd` / 编辑文档 | 增加目标类型与参数编辑，接入撤销、重做、保存；当前仍需元数据 JSON |
| `schemas/level.schema.json` 和回归测试 | 同步格式约束，验证旧地图兼容、暂停、重置、程序结束及同 tick 结果 |

目前没有现成的 `GoalRegistry`。若之后做目标注册表，应由可信代码注册解析和判定实现，再由 JSON 选择名称；不要让 JSON 执行任意脚本。

## 4. 新模块怎么写

### 4.1 模块定义字段

| 字段 | 必填 | 含义与当前约束 |
| --- | --- | --- |
| `format_version` | 是 | 当前为 `1` |
| `id` | 是 | 内容定义 ID，例如 `example.attack` |
| `name` | 是 | 显示名称，可写中文，不能为空 |
| `description` | 否 | 说明文字，默认空串 |
| `size.width` / `height` | 是 | 真实矩形占地宽高，单位为格，每项为 `0.001..256` 的有限数值 |
| `texture` | 是 | 已存在、可解码的图片资源路径 |
| `script_type` | 是 | 行为注册名称，例如当前的 `MovementModule` |
| `properties` | 否 | 行为参数对象，公共默认值为 `{}`；具体行为可能要求必填参数 |

当前 `MovementModule` 要求 `properties.move_speed` 为有限正数，单位为格/秒；多个可用移动模块的速度贡献相加。修改速度或外观时继续用 `MovementModule`，不需要为每个内容变体写一个行为类。

`script_type` 不是 `.gd` 文件地址；把它写成 `res://scripts/...gd` 不能加载脚本。注册名称与模块 `id` 可以不同：多个模块定义可以引用同一种行为。

### 4.2 全新攻击模块需要哪些代码

文末攻击示例使用建议注册名 `AttackModule`，以及三个**尚未实现**的专用属性：

| 建议属性 | 示例值 | 约定 |
| --- | --- | --- |
| `properties.damage` | `10` | 每次有效命中造成的伤害量，有限正数 |
| `properties.range` | `3.0` | 最大攻击距离，单位为格，有限正数 |
| `properties.cooldown_seconds` | `0.5` | 两次成功攻击间的最短间隔，有限正数；当前 tick 频率下为 `5` tick |

这些字段只描述一类攻击模块的静态参数；攻击对象、索敌方法、伤害接收对象、弹道、命中方式、视线阻挡和友军伤害，仍须由对应行为与战斗设计明确。`collision` 和 `radar_block` 不会自动为攻击实现子弹阻挡。

实现步骤：

1. 新建继承 `ModuleBehavior` 的可信 GDScript，例如 `scripts/modules/attack_module.gd`，为函数写中文用途注释。
2. 在 `validate_definition()` 中验证攻击专用属性的类型、范围和单位。当前基类只有通用校验与移动速度接口，需要新增明确的攻击能力接口，不能仅给 `get_move_speed()` 换名字。
3. 在 `ModuleBehaviorRegistry.create_default()` 中注册 `AttackModule`，或让同一行为注册表作为依赖贯穿装配与运行流程。当前 `AssemblyModel.build_document()` 和 `GameSession.run()` 创建世界时使用默认行为表；只在一个局部变量中注册，不会让正式游戏自动使用它。
4. 增加攻击命令、目标解析、冷却推进与伤害结算。保持世界数据与 UI 分离，并沿用计算后统一提交的结构，明确同 tick 的攻击、死亡和胜利判定顺序。
5. 将当前冷却、血量等放在运行时实例或独立运行状态中，不能写回共享 `ModuleDefinition.properties` 或关卡原件。当前 `ModuleInstance` 并没有攻击冷却、血量字段，这些需要新增。
6. 若玩家通过代码主动攻击，扩展 Lexer、Parser、AST、执行器及对应的可用能力检查。当前仅支持 `main()` 和 `move`；写上 `attack()`、`fire()` 或 `gun.attack()` 都不会自行生效。最终指令名称与参数应先按语言设计确定，本文不把任何一个写法当成现有语法。
7. 在 `module.schema.json` 中为 `AttackModule` 增加专用属性约束，并补充行为、冷却、目标失效、射程边界、重复运行隔离和 DSL 错误定位测试。

内容层目前允许合法但尚未注册的 `script_type`：它可能出现在模块列表中，且可以暂存为装配草稿。但确认装配时会通过 `MachineFactory` 创建行为，届时未注册的 `AttackModule` 会被明确拒绝。**模块显示出来不代表攻击已经实现。**

### 4.3 让关卡允许安装新模块

完成注册和内容加载后，还要修改地图的 `properties.level.allowed_modules`，加入模块的**内容 ID**，例如 `example.attack`，不能填注册名 `AttackModule`。如果希望安装一个移动模块和一个攻击模块，`module_limit` 至少为 `2`。

`allowed_modules` 只控制可安装的模块类型，并不是新的 DSL 指令白名单。未配置它时，当前代码从 `player_spawn.modules` 的类型推导允许列表；未配置 `module_limit` 时，从该模板的模块数量推导，至少为 `1`。建议内容作者显式写出这两个规则。

地图中的 `player_spawn.modules` 是格式与默认规则的来源，不会自动替玩家装好机器。玩家进入正常关卡或编辑器测试时，仍从空装配开始。

模块定义 ID、行为名称和实例名有不同用途：

| 例子 | 用途 |
| --- | --- |
| `example.attack` | 内容 ID，写在 `allowed_modules` 和实例的 `module_id` 中 |
| `AttackModule` | 行为注册名称，只写在模块定义的 `script_type` 中 |
| `gun_left` | 同一机器中的实例名，写在装配条目的 `id` 中 |

实例名必须为非保留的英文标识符：字母或下划线开头，其后仅字母、数字、下划线；同一机器内不能重复。不要直接把带点号的内容 ID 当成实例名。

### 4.4 尺寸和装配规则

默认模块大小为 `0.5 × 0.5` 格；玩家装配的中心偏移网格为 `0.5`，范围 `-4..4`。首个模块必须位于 `(0,0)`，其他模块必须与任意已有模块实际共边，允许分支，角点接触不算。确认时还要求中心存在、全部模块沿边连通且出生占地可通行。

因此，定义文件接受某个尺寸，不保证它在当前装配网格上容易拼装。例如两个宽 `1` 的模块需要中心间距 `1` 才能水平共边；不能把所有模块的相邻偏移都写死为 `0.5`。文末攻击模块使用 `0.5 × 0.5`，可与默认移动模块按半格间距共边。

## 5. 新地块怎么写

### 5.1 地块定义字段

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `format_version` | 是 | 当前为 `1` |
| `id` | 是 | 稳定地块 ID，例如 `example.obstacle` |
| `name` | 是 | 地块显示名，不能为空 |
| `texture` | 是 | 图片路径；外观不决定是否通行 |
| `collision` | 是 | `true` 阻止机器通行，`false` 允许通行 |
| `radar_block` | 是 | 雷达遮挡配置，目前只保存，尚无雷达系统执行它 |
| `properties` | 否 | 地块扩展属性对象，默认 `{}` |

当前地块没有 `script_type` 或自定义 `size` 的行为入口。一个地图地块占一个 `1 × 1` 的格子；模块的尺寸规则不能套用到地块文件上。

### 5.2 普通障碍物现在即可配置

要做一格不可通行的障碍物，将 `collision` 设为 `true` 即可。加载后它会出现在编辑器画笔列表中，绘制到地图时记录的是该定义的 `id`。

碰撞检查机器每个模块的真实矩形及完整移动路径，不能靠高速移动越过障碍物。出生模块也不能与障碍物相交。`collision: true` 当前表示阻止移动，不表示“触碰伤害”“可以被打碎”或“阻挡子弹”。

障碍物与 void 的区别是：障碍物是明确放置、可显示纹理、可记录属性的地块；void 是没有指定地块的位置或地图之外的区域。两者都不可通行，但不能把 void 注册成地块，也不能在地图中写 `tile_id: void`。

### 5.3 地图中如何引用地块

地图的 `tiles` 数组每项包含 `x`、`y`、`tile_id`。坐标是图内整数，从零开始；同一个坐标只能出现一次。如果某格原来是地板，改成障碍物时应替换该项的 `tile_id`，不能再追加一个同坐标项。

地块坐标 `(2,1)` 对应机器坐标中心 `(2.5,1.5)`。地图宽高是 `1..256`；未在 `tiles` 中列出的所有位置都为 void。只有定义了障碍物文件，却没有在地图中引用它，不会改变地图。

### 5.4 地块需要额外玩法时

例如 `properties.damage_per_second`、`friction`、`max_health` 都可以作为扩展数据保存，但当前不会自动被读取。新增伤害地面、减速区域或可破坏障碍物时，需要同时实现：

1. 参数的 Schema 与运行时校验。
2. 角色与地块接触或进入/离开区域的判定。
3. 对速度、伤害或地块状态的世界结算。
4. 实例状态的存储与重开重置。可破坏地块的当前血量不能存入共享的地块定义，破坏结果也不能直接改写作者原始地图。
5. 对应编辑器展示、提示以及回归测试。

## 6. 编辑、保存与验证时需要注意

### 6.1 避免覆盖已有数据

在地图编辑器的“元数据 JSON”窗口中，修改**现有对象内**的 `properties.level`，保留同级字段。`MapEditorDocument.apply_metadata()` 对传入的 `properties` 是整体替换，不会递归合并；不能只传一小段新的 `goal` 属性后，假定模块上限和允许列表会自动保留。

地图未知顶层字段通过 `MapDocument.extra` 保存，并由 `MapDocument.to_dict()` / `MapCodec` 往返；`properties` 等扩展字段也会保留。写原始地图文件时，自定义字段可按地图格式放在顶层或 `properties`，不要把编辑器元数据窗口中的 `extra` 包装误认为必须新增的地图标准字段。

模块和地块定义的未知字段目前保留在 `definition.raw` 中，专用属性另存到 `definition.properties`。它们没有 `to_dict()` 方法；修改结构化属性也不会自动同步 `raw`。如果以后制作模块定义编辑器，需要单独实现保留未知字段的保存逻辑。

### 6.2 需要同步修改哪些地方

| 改动 | JSON | Schema | 校验和运行代码 | 编辑器 |
| --- | --- | --- | --- | --- |
| 移动模块参数变体 | 新模块定义、允许列表 | 沿用现有 | 沿用现有 | 重载内容即可 |
| 不可通行障碍物 | 新地块定义、地图格子引用 | 沿用现有 | 沿用现有 | 重载后可用画笔绘制 |
| 存活时间条件 | 新类型的 `goal` | 扩展关卡 Schema | 必须实现判定与持续模拟 | 需要目标参数界面；初期可用元数据窗口 |
| 攻击模块 | 新行为定义、允许列表 | 扩展模块专用字段 | 必须实现行为、结算及程序入口 | 目录可复用；额外参数或状态界面按需增加 |

编辑器保存成功不等于关卡能运行：地图草稿可以没有出生点；模块 JSON 可以引用尚未注册的行为；未知属性也可能只是被保留。必须经过完整的关卡和装配验证。

### 6.3 验证顺序

1. 检查 JSON 语法，并选择对应 Schema 校验结构。
2. 重载内容，确认没有重复 ID、图片错误、字段类型错误。
3. 打开地图，检查 `allowed_modules`、上限、地块引用和出生点。
4. 点击编辑器“校验”“开始测试”，确认使用当前配置；空装配阶段主动安装模块并确认。
5. 测试成功和失败边界：障碍物挡路、出生占地被挡、目标缺失或类型未知、计时暂停/重置、攻击冷却与射程等。
6. 保存并重新打开，核对自定义字段与关卡规则；另在同一编辑会话内验证撤销/重做。重新打开文件会清空编辑历史，历史不会写入地图 JSON。正式关卡与编辑器试玩都应覆盖。
7. 修改运行逻辑后执行工程根目录的 `tools/test.ps1`，同时检查引擎错误与测试完成标记。新增能力还需要新增针对该能力的用例，旧测试通过不代表新能力已经正确。

编辑器试玩只在本次会话中保留程序与装配；返回编辑器后结束，不写正式 `solutions` 或通关记录。测试目标判定时应分别检查“会话能获胜”和“正常关卡进度正确保存”，不能混为一项。

## 7. 完整 JSON 文件示例

以下代码块均为标准 JSON，没有注释或省略号。除明确标为字段片段的代码块外，可以分别复制成文件。建议先读每个例子的支持状态，再决定是否放进当前游戏目录。

### 7.1 存活 60 秒关卡：`survive_60_seconds.json`

**状态：格式提案，必须先实现第 3 节的目标解析、计时与存活判定，当前游戏不能运行。**

实现完成后可放在 `user://levels/survive_60_seconds.json`，或作为工程内置关卡放在 `data/levels/`。这里写的是完整地图，而不是单独的条件文件。例子只依赖现有 `movement` 和 `floor`，不依赖下方尚未实现的攻击模块。

```json
{
  "format_version": 1,
  "id": "example.survive_60_seconds",
  "name": "存活六十秒",
  "width": 3,
  "height": 3,
  "tiles": [
    {"x": 0, "y": 0, "tile_id": "floor"},
    {"x": 1, "y": 0, "tile_id": "floor"},
    {"x": 2, "y": 0, "tile_id": "floor"},
    {"x": 0, "y": 1, "tile_id": "floor"},
    {"x": 1, "y": 1, "tile_id": "floor"},
    {"x": 2, "y": 1, "tile_id": "floor"},
    {"x": 0, "y": 2, "tile_id": "floor"},
    {"x": 1, "y": 2, "tile_id": "floor"},
    {"x": 2, "y": 2, "tile_id": "floor"}
  ],
  "player_spawn": {
    "position": {"x": 1.5, "y": 1.5},
    "modules": [
      {"id": "drive", "module_id": "movement", "offset": {"x": 0, "y": 0}}
    ]
  },
  "enemies": [],
  "objects": [],
  "dialogue": [],
  "properties": {
    "level": {
      "order": 10,
      "description": "运行开始后，保持存活六十秒即可获胜。",
      "module_limit": 1,
      "allowed_modules": ["movement"],
      "goal": {
        "type": "survive_time",
        "duration_seconds": 60
      },

```

空的 `main()` 用来验证“程序完成后仍继续计时”的新规则。这个例子没有敌人或其他威胁，只演示目标配置与计时；不能据此认为敌人、伤害和死亡已经实现。不要为了让旧版解析通过而给该 `goal` 加上 `position`，否则旧版会按到达位置判胜。

### 7.2 攻击模块：`attack.json`

**状态：公共定义结构可被当前内容层读取，但 `AttackModule` 和以下攻击属性属于提案，未注册和实现前不能确认包含它的装配，也不能进行攻击。**

实现并注册行为后，可放在 `user://data/modules/attack.json` 或 `data/modules/attack.json`。本例复用已有移动模块图片，保证引用真实存在；这只是示例外观，不代表它会提供移动能力。制作自己的攻击图片后，再替换 `texture`。

```json
{
  "format_version": 1,
  "id": "example.attack",
  "name": "攻击模块",
  "description": "每次有效命中造成十点伤害，射程三格，攻击间隔半秒。",
  "size": {
    "width": 0.5,
    "height": 0.5
  },
  "texture": "res://assets/modules/movement.svg",
  "script_type": "AttackModule",
  "properties": {
    "damage": 10,
    "range": 3.0,
    "cooldown_seconds": 0.5
  }
}
```

示例攻击模块没有移动速度。要让机器同时能移动和攻击，应由玩家另装 `movement`，并让关卡允许列表包含 `movement`、`example.attack`，上限至少为 `2`。

下面是**合并到现有地图的 `properties.level` 内部的字段片段，不是独立关卡文件**；目标、初始程序和其他规则应保留。只有攻击行为已经实现并注册后，这个组合才能实际使用。

```json
{
  "module_limit": 2,
  "allowed_modules": ["movement", "example.attack"]
}
```

### 7.3 障碍物地块：`obstacle.json`

**状态：可以使用当前已有的地形阻挡功能，不需要新增地块行为代码。**

放在 `user://data/tiles/obstacle.json` 或 `data/tiles/obstacle.json`。本例复用现有地板图片，因此初始外观会与地板相同，但它不可通行。实际制作时应准备能明显区分障碍物的图片，再修改 `texture`；不要把尚不存在的图片路径直接填进去。

```json
{
  "format_version": 1,
  "id": "example.obstacle",
  "name": "障碍物",
  "texture": "res://assets/tiles/floor.svg",
  "collision": true,
  "radar_block": true,
  "properties": {}
}
```

其中 `collision: true` 现在就参与机器通行判定；`radar_block: true` 只是为未来雷达系统保存配置，目前没有实际雷达遮挡效果。
